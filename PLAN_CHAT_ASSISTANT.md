# План реализации чат-помощника

Документ описывает цели, требования и поэтапные планы внедрения чат-помощника внутри KP Generator. Приведено два варианта архитектуры: локальный rule-based помощник и гибридный LLM с использованием внутренних данных. Пункты внутри этапов сгруппированы от обязательного к желательному.

## 1. Цели и требования
1. Предоставлять пользователям быстрые ответы по функционалу, справочникам, ошибкам расчётов и настройкам маржи/логистики.
2. Подсказывать оптимальные параметры расчёта на основе истории генераций и справочников.
3. Работать внутри защищённого контура (учитывать роли пользователей, избегать утечек коммерческих данных).
4. Логировать диалоги для обучения и аудита.
5. Масштабироваться под новые источники знаний (инструкции, FAQ, аналитика).

## 2. Общие подготовительные шаги
1. Аудит внутренних данных: инструкции, `docs/`, история генераций, справочники. Определить, что можно раскрывать пользователям (и каким ролям).
2. Создать единый формат знаний: markdown/JSON с тегами, датами, версиями, ссылками на разделы UI.
3. Определить сценарии использования (FAQ, подсказки при ошибках формы, помощь в админке).
4. Разработать UX: панель чата на страницах, всплывающее окно, горячие клавиши.
5. Подготовить API-слой для получения данных о пользователе, контексте страницы, последнем действии.
6. Настроить логи: запросы пользователей, ответы ассистента, эскалации к человеку.

## 3. Вариант A: Локальный rule-based ассистент
### Архитектура
- База знаний в виде JSON/SQLite + полнотекстовый поиск (Whoosh, SQLite FTS5).
- Модуль диалогов в Flask (`app/services/chatbot/rules.py`), который использует шаблоны ответов.
- Коннектор к истории генераций для вычисления подсказок (SQLAlchemy queries).

### Этапы внедрения
1. **Сбор знаний**: сформировать FAQ по функционалу, структуру инструкций, список типовых ошибок валидации/генерации.
2. **Нормализация**: привести знания к схеме `{id, tags, question_patterns, answer_template, priority}`.
3. **Поисковый движок**: внедрить FTS-поиск по описаниям. Возможный стек: SQLite FTS, `rapidfuzz` для нечеткого поиска.
4. **Контекст пользователя**: определить middleware, который передает в ассистент активную страницу, роль, последние ошибки формы.
5. **Диалоговый движок**:
   - Если найдено точное совпадение по шаблону — использовать шаблон с подстановками (например, текущая маржа, компания).
   - При нескольких результатах — выдавать список предложений.
   - При отсутствии — возвращать fallback с ссылкой на инструкции.
6. **Подсказки по расчётам**:
   - Реализовать сервис рекомендаций: анализировать историю пользователя, вычислять среднюю маржу, типовые логистические затраты.
   - Возвращать советы (`"Для логистики в Уфу среднее значение 180 000 ₽"`).
7. **UI интеграция**: виджет с историей сообщений, кнопки «вставить в форму» / «открыть инструкцию».
8. **Расширение знаний**: автоматическая выгрузка из `docs/`, `instructions_page`, админских распоряжений.

### Плюсы / Минусы
- **Плюсы**: полная автономность, предсказуемость ответов, отсутствие затрат на LLM.
- **Минусы**: ограниченная вариативность ответов, сложность поддержки при росте сценариев.

## 4. Вариант B: Гибридный LLM + внутренняя RAG база
### Архитектура
- Локальный или облачный LLM (например, GPT-4o mini, Azure OpenAI) с Retrieval-Augmented Generation.
- Векторное хранилище (Chroma, FAISS) с документами: инструкции, справочники, история генераций (обезличенная).
- Middleware, который формирует промпт с учётом роли пользователя и ограничений.

### Этапы внедрения
1. **Безопасность**: определить, какие данные можно отправлять в LLM, настроить анонимизацию (замена названий компаний на коды).
2. **Хранилище знаний**:
   - Конвертировать все документы (`docs/`, `PLAN_IMPROVEMENTS.md`, `instructions`) в chunks.
   - Добавить метаданные: раздел, версия, роль доступа, дата обновления.
   - Индексировать через векторный стор.
3. **API-слой**:
   - Сервис Retrieval: принимает запрос, контекст пользователя, возвращает релевантные chunks.
   - Контроллер, который вызывает LLM с промптом вида: `context + пользовательский вопрос + ограничения (не придумывать данные вне контекста)`.
4. **Интеграция с бизнес-логикой**:
   - Предоставить LLM функции: `get_user_stats`, `get_recent_generations`, `suggest_margin(company, product)` — через инструменты/функции в промпте.
   - Ограничить вызовы по ролям (админ, менеджер).
5. **UI и диалог**:
   - Показывать не только ответ, но и источники (ссылки на инструкции или справочники).
   - Добавить кнопки «скопировать в форму», «создать КП с этими параметрами».
6. **Тестирование и observability**:
   - Набор сценариев (вопрос → ожидаемый ответ).
   - Логирование промптов и ответов с PII-маскированием.
   - Мониторинг стоимости запросов (если облачный LLM).
7. **Эскалация**:
   - Если LLM не уверен или не нашёл данных — отправлять пользователю форму связи с администратором или ссылку в документацию.

### Плюсы / Минусы
- **Плюсы**: гибкие ответы, возможность обучать ассистента на истории, масштабируемость на новые сценарии.
- **Минусы**: зависимость от LLM, необходимость строгой безопасности и контроля затрат.

## 5. Комбинированная стратегия
1. Запустить rule-based ассистента как MVP, собрать статистику вопросов.
2. Параллельно строить базу знаний в формате, пригодном для RAG.
3. На этапах повышенной критичности (админские операции, расчёты с реальными данными) использовать rule-based ответы; для общих вопросов — LLM.
4. Обеспечить переключение режима per-role (например, пользователи получают LLM-ответы, админы — rule-based шаблоны для чувствительных операций).

## 6. Ресурсы и организационные шаги
1. Назначить роль «куратор знаний», который обновляет FAQ/инструкции и валидирует ответы ассистента.
2. Обеспечить доступ к тестовому окружению с копией БД (обезличенные данные) для отладки.
3. Подготовить чек-листы QA: корректность ответов, устойчивость к неточным запросам, скорость реакции.
4. Разработать процедуру отката и отключения ассистента (feature flag, переменная окружения).
5. Запланировать обучение пользователей и сбор обратной связи через форму в приложении.
